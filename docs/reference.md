## Reading the icons

Each corner of a 16px icon means one thing and shows at most one mark:

| Corner | Means | Examples |
| --- | --- | --- |
| Top-left | What a TypeScript, JavaScript, or Python source file does | square web controller, envelope listener, ring service, cube entity |
| Top-right | Something to act on, or live now; the most urgent wins | red stop sign for an unignored secret, amber triangle for a warning, ring for a running service or active profile, dot for the module accent |
| Bottom-left | The environment | red circle production, amber diamond staging, green triangle test, blue square local |
| Bottom-right | Part of the artwork | Kubernetes kinds, folder glyphs, Spring Modulith locks |

Source and test roots get a colored outline, blue and green in the default artwork colors; resources roots get amber stacked lines. A colored fill or dot marks a service, a folder with a Gradle, Maven, or Node manifest, or a module, and tells them apart. Folder color is never a status. Test stereotypes share one magenta hue, so a test never looks like production code.

Java and Kotlin classes with a role show it as the class icon itself: a green hexagon with a power symbol for the application, a blue window for a web controller, an amber cylinder for a repository, a magenta flask for a test.

In the IDE, **View > Emberkai Icons > Icon Legend…** (also under **Tools**) shows every mark drawn as the Project view draws it, in the current accessibility mode. Hover a file in the Project view for a short description, or right-click it, or its editor tab, and choose **Explain This Icon** to see what each of its marks means.

Java and Kotlin declarations, source files, and compiled Java classes keep their native IntelliJ icons and modifier badges. Gradle Kotlin build scripts (`*.gradle.kts`) use Gradle icons; other files and folders use Emberkai's icons.

IntelliJ supplies visibility, static/final, runnable/test markers, read status, and registered icon layers. Nested types keep their own icons. Specialized framework providers, including live test status, take priority; methods, fields, type parameters, and package/module descriptors retain their native presentation. Java source-root integration loads only when the IDE's Java plugin is available; Kotlin's native icons come from the Kotlin plugin. Other files and folders use Emberkai's icons.

## Class and source roles

Spring, Quarkus, Micronaut, and JPA classes show a stereotype icon in place of the native type icon (the letter in a circle), each with its own shape and color. IntelliJ's own marks, such as abstract, final, runnable, and test, and the visibility column are layered on it as before, and Kotlin classes keep the small Kotlin mark. Entry points, where work enters a service from outside, come first:

- a hexagon with a power symbol for `@SpringBootApplication`;
- a browser window for web controllers: `@RestController`, `@Controller`, JAX-RS `@Path`, and Micronaut `@Controller`;
- an envelope for message listeners: `@KafkaListener`, `@RabbitListener`, `@JmsListener`, `@SqsListener`, and MicroProfile `@Incoming` on a method, or Spring and Micronaut `@KafkaListener`/`@RabbitListener` on the class;
- an hourglass for scheduled jobs: Spring, Quarkus, or Micronaut `@Scheduled` (or `@Schedules`) on a method.

Then the roles a class plays inside the service:

- an arrow tag for HTTP clients: `@FeignClient`, `@HttpExchange` or a `@GetExchange`/`@PostExchange`/… method, MicroProfile `@RegisterRestClient`, and Micronaut `@Client`;
- a cylinder for repositories: `@Repository`, `@RepositoryDefinition`, Micronaut Data `@Repository`/`@JdbcRepository`/`@R2dbcRepository`, or a type extending a Spring Data, Micronaut Data, or Panache repository such as `JpaRepository` or `PanacheRepository`;
- a ring for `@Service` and CDI `@ApplicationScoped`;
- a rounded toggle for configuration: `@Configuration`, `@AutoConfiguration`, `@ConfigurationProperties`;
- a cube for persistent entities: Jakarta or `javax` `@Entity`, MongoDB `@Document`, Micronaut Data `@MappedEntity`.

Test classes show what they start, most expensive first:

- a shipping container for tests that start containers: Testcontainers `@Testcontainers` and Spring Boot `@ImportTestcontainers`;
- a flask for tests that start the whole application: `@SpringBootTest`, `@QuarkusTest`, `@QuarkusIntegrationTest`, and Micronaut `@MicronautTest`;
- a test tube for Spring Boot test slices, which start only part of it: `@WebMvcTest`, `@WebFluxTest`, `@RestClientTest`, `@WebServiceClientTest`, `@GraphQlTest`, `@JsonTest`, `@DataJpaTest`, `@JdbcTest`, `@JooqTest`, `@DataJdbcTest`, `@DataR2dbcTest`, `@DataMongoTest`, `@DataRedisTest`, `@DataCassandraTest`, and `@DataElasticsearchTest`, from their Spring Boot 3 packages or the Spring Boot 4 test modules.

A plain Spring `@Component` gets an indigo puzzle piece when none of the roles above matches. `@Service`, `@Repository`, `@Configuration`, and the other stereotypes keep their own icons when a class carries both annotations.

TypeScript and JavaScript files keep their file icon and get the same roles as a small glyph in its top-left corner, with a leaf for the application and a plain square for web controllers. Each file belongs to the nearest `package.json` above it, within the project's content root:

- the web-controller square for Next.js routes: `page` and `route` files and metadata routes (`sitemap`, `robots`, `manifest`, `icon`, `apple-icon`, `opengraph-image`, `twitter-image`) under `app/`, files under `pages/` (API routes under `pages/api/`; tests and stories such as `index.test.tsx` are skipped), and `middleware` or `proxy` at the app root or in `src/`. An app is the nearest folder with a `next.config.*`, so each app in an Nx or Turborepo workspace counts, or else a package that depends on `next`. As in Next.js, `src/app` and `src/pages` are ignored when `app/` or `pages/` sits next to `src/`, and files and folders starting with `_`, such as `_app.tsx` or `app/_components/`, are private to the router;
- for NestJS, TypeORM, MikroORM, and Mongoose (in a package that depends on `@nestjs/common`, `@nestjs/core`, `typeorm`, or `@mikro-orm/core`), the decorator as imported from the module that defines it, including aliases, default-plus-named, namespace (`@common.Controller()`), subpath, and CommonJS `require` imports: the square for `@Controller` and GraphQL `@Resolver`; the envelope for `@WebSocketGateway`, `@MessagePattern`, `@EventPattern`, `@OnEvent`, and BullMQ `@Processor`; the hourglass for `@Cron`, `@Interval`, and `@Timeout`; the ring for `@Injectable`; the toggle for `@Module`; and the cube for TypeORM and MikroORM `@Entity` and Mongoose `@Schema`. A file with several takes the first in the order above, so a service with a `@Cron` method shows the hourglass. Guards, pipes, interceptors, exception filters, middleware, and Passport strategies are `@Injectable` too, but they wrap requests rather than serve them, so they get no ring: by name (`*.guard.ts`, `*.pipe.ts`, `*.interceptor.ts`, `*.filter.ts`, `*.middleware.ts`, `*.strategy.ts`) or by the interface they implement. Comments are ignored, so commented-out code and JSDoc examples never count.

Next.js routes need no file reads. NestJS files are read, up to 256 KB and cached until they change, only inside packages that depend on one of those libraries. Where reading from disk would block the UI thread, such as an editor tab or scope-based file colors, only results a background lookup has already cached are used, so such a surface can miss a badge until it next repaints, for example after the Project view has shown the file and the tab is reopened. Badges refresh when the project's own `package.json` or `next.config.*` changes, once per burst, so installing packages does not repaint the project. Files in `node_modules`, declaration files (`*.d.ts`), and excluded folders are left alone.
Python files get the same roles as a small glyph in the top-left corner of their file icon. A file belongs to the nearest folder, within its content root, with a `pyproject.toml`, `setup.py`, `setup.cfg`, `Pipfile`, `requirements.txt`, `requirements.in`, or Django `manage.py`. It is read, up to 256 KB and cached until it changes, only when one of those names FastAPI, Flask, Django, Django REST framework, Celery, Dramatiq, FastStream, APScheduler, SQLAlchemy, SQLModel, Flask-SQLAlchemy, pydantic-settings, or Testcontainers. A role counts only when the module imports what it uses:

- the web-controller square for route decorators on a FastAPI app or `APIRouter`, a Flask app or `Blueprint`, or a Django Ninja API or router that the module creates (`router = APIRouter()`, then `@router.get(…)`) or imports under a conventional name (`app`, `api`, `router`, `api_router`, `bp`, or `blueprint`); Django class-based views and Django REST framework views and viewsets; `@api_view`; and Django's `require_http_methods`, `require_GET`, `require_POST`, and `require_safe`;
- the envelope for Celery `@shared_task` and `@app.task` (on a `Celery()` app the module creates, or one it imports as `app`, `celery`, or `celery_app`, or from a module with `celery` in its name), Dramatiq `@dramatiq.actor`, FastStream `@broker.subscriber`, and Django `@receiver` signal handlers;
- the hourglass for APScheduler `@scheduler.scheduled_job`;
- the cube for Django models, SQLAlchemy models with a `__tablename__`, Flask-SQLAlchemy `db.Model` classes, and SQLModel classes with `table=True`;
- the toggle for pydantic-settings `BaseSettings` subclasses and Django `AppConfig`.

In test modules (`test_*.py`, `*_test.py`, and `conftest.py`), the shipping container marks modules that import Testcontainers, and the flask marks modules that use FastAPI's or Starlette's `TestClient` or subclass Django's `TestCase`, `TransactionTestCase`, or `LiveServerTestCase`, or their Django REST framework counterparts. Comments and docstrings are ignored, so an example in a docstring counts for nothing. Routes, views, listeners, and jobs join the **Emberkai: Entry points** scope and the **Entry points** lens. Badges update when a project manifest changes, and follow the **Class stereotype icons** setting.

When a class matches several, the first in these lists wins, so a `@Service` with a `@Scheduled` method shows the hourglass, and a `@DataJpaTest` with `@Testcontainers` shows the container. The icon appears on class nodes, and on file nodes and editor tabs when the file's icon comes from its single class. Annotations on the class and on its own methods are matched by name against the file's imports, read from stubs without resolving references, so `@EventListener`, meta-annotations, and look-alikes from other packages are ignored. Turn them off with **Class stereotype icons** in settings or the **View > Emberkai Icons** menu; Explain This Icon and Project view tooltips name the stereotype and, for method annotations, the method, such as *Scheduled job stereotype (@Scheduled on purge())*.

## Tool icons

Includes GitHub Actions workflows and repository templates, AI assistant instructions, Azure Pipelines, Bitbucket Pipelines, Dev Containers, Renovate, and Maven icons for `pom.xml`, `.pom`, wrapper files, and `.mvn/` configuration. Azure and Bitbucket CI YAML is recognized by its conventional filename; unrelated YAML files keep their usual icons. Azure Pipelines and Bitbucket folders use matching artwork.

## Settings

Open **Settings > Appearance & Behavior > Emberkai Icons** to choose whether Java/Kotlin files use IntelliJ's native icons, color service folders containing a Gradle, Maven, or Node package manifest, select a service-folder palette, use module-aware accent colors, and enable or disable context-aware icon categories. A **Preset** at the top of the page sets them all at once: **Icons only** keeps tool icons and drops badges, markers, and tooltips; **Recommended** is the default; **Everything** also turns on module accents and JVM architecture folders. Presets leave native icons, folder colors, the palette, and accessibility options alone, and the picker shows **Custom** once single features differ. Single features sit under **Advanced**, grouped by what they show: **Tool icons**, **Badges and warnings**, **Markers and hints**, and **Tooltips and ownership**. The filter field narrows the page, matching option names and section titles, and searches **Advanced** too, so *warnings* shows every warning badge, and **Export…**, **Import…**, and **Reset to defaults** manage everything on that page. The live project-tree preview follows unsaved settings. Accessibility options include shape-coded high-contrast markers, monochrome service folders, and reduced folder color. Known production, staging, test, and local variants of Spring profiles, Docker Compose files, Helm values, and `.env` files receive shape-and-color badges. Environment folders get the same badge: a child of `overlays/`, `envs/`, `env/`, `environments/`, `clusters/`, or `stages/` whose name contains one known environment, such as `overlays/production/` or `clusters/prod-eu-west-1/`. Configuration files inside them (YAML, JSON, Jsonnet, Terraform/HCL, properties, TOML, INI, XML, CUE, and `Kustomization`) inherit the nearest environment folder's badge up to six levels down, and join the **Production config** scope when it is production; a file's own name wins, and docs and sources are left alone. Disable **Environment variant badges** independently of their base icons. Production files, by name or inherited from a production environment folder, also get a red-tinted editor tab and a banner that says why they count as production, so the warning stays visible after the file is opened; turn each on or off under **Settings > Appearance & Behavior > Emberkai Icons > Editor Warnings**, which presets leave alone, or hide the banner with its own link. Likely secrets that are inside a VCS root but not ignored get a red stop-sign badge with an exclamation mark; disable **Unignored secret warning badges** to hide it. Spring profile files that the selected run configuration activates get a ring-and-dot live marker in the top-right corner; disable **Active Spring profile markers** to hide it. While a run or debug session is live, the module folder that owns it gets a dot-in-ring running marker in the same corner (green while running, amber while debugging), and its tooltip names the configuration and, for Spring Boot, the port; disable **Running-service markers** to hide it. The **View > Emberkai Icons** menu also has quick toggles for folder colors, module-aware accents, accessibility modes, JVM architecture folders, and class stereotype badges. Standard filename and extension mappings remain available when a context category is disabled. Applying settings refreshes project trees and open editor tabs; other IDE surfaces may need reopening to request updated icons.

## Badges and warnings

The unignored-secret badge covers `.env` and `.env.*` (except `.env.example`, `.env.sample`, `.env.template`, `.env.dist`, `.env.defaults`, and variants such as `.env.local.example`), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `id_rsa`, `id_ed25519`, `id_ecdsa`, `id_dsa` (not `.pub`), `.netrc`, `.pypirc`, `credentials.json`, and `service-account*.json`. `secrets.yaml` is left out because it is often encrypted. `.npmrc` and `.yarnrc.yml` are committed on purpose, so they get the badge only when they hold a literal registry credential: `_authToken`, `_auth`, or `_password` in `.npmrc`, also scoped to a registry as in `//registry.npmjs.org/:_authToken=…`, or `npmAuthToken` or `npmAuthIdent` in `.yarnrc.yml`. Values that reference an environment variable, such as `${NPM_TOKEN}` or `$NPM_TOKEN`, are how these files are meant to be shared and are left alone, as are comment lines and empty or `null` values; **Explain This Icon** lists each credential's line. Kubernetes manifests with a plaintext Secret get the same badge: a core `v1` `Secret` whose `data` or `stringData` has a value in the file, since base64 is an encoding, not encryption. Values built from `{{ … }}` templates or `${…}` variables, Secrets without values, and files that SOPS encrypted are left alone, and **Explain This Icon** lists each Secret with its line and keys. Tracked and untracked-but-not-ignored files both count. Files outside a VCS root, and files whose ignore status the IDE has not computed yet, keep their normal icons. The badge reads IntelliJ's cached change-list state, so icon lookups never run VCS commands; icons refresh after VCS status updates, such as a `.gitignore` edit. The badge is drawn in black when high-contrast or monochrome folders are enabled, and **Explain This Icon** says why it appears. It needs the IDE's VCS support; without it, no badge is shown.

Each badge has a fixed corner, and each corner shows one badge, so a 16px icon never carries more than its artwork and two small marks. The top-right shows the one thing to act on or that is live now, and the most urgent wins: an unignored secret, then an amber warning, then a running or live-profile marker, then the module accent dot. The bottom-left shows the environment. The bottom-right belongs to the artwork, where folder glyphs, Kubernetes kind badges, and Spring Modulith locks sit, and stereotype glyphs keep the top-left of TypeScript and JavaScript file icons; Java and Kotlin classes show their stereotype as the class icon. A badge that is not drawn still appears in the Project view tooltip and in **Explain This Icon**, so a production `.env` file that is not ignored and lacks a key its siblings define shows the production badge and the secret badge, and lists the missing key.

## Module accent colors

Right-click a module folder and choose **Assign Module Accent Color…** to pin its accent, or pick **Automatic** to return to the module-name default. **Tools > Reset All Module Accent Colors** clears every override. Pinned colors are stored with the project in `.idea/emberkai-module-accents.xml`.

## Explain This Icon, tooltips, and the coverage audit

In the Project view or on an editor tab, right-click a file or folder and choose **Explain This Icon** to see its light/dark preview, what each mark on it means, the winning mapping key and source, matching context rule, and whether native icon policy or a project role took precedence. Copy the mapping key, open the artwork, or choose **Override This Icon…** to create a project-local exception. Overrides live in `.idea/emberkai-icons.properties`, can reference bundled artwork or SVGs in `.idea/emberkai-icons/`, and can be committed with the repository. **Tools > Open Icon Overrides File**, **Reload Icon Overrides**, and **Browse Bundled Icons** manage them; native IDE icons still take precedence.

Hovering a file or folder in the Project view shows what Emberkai recognized, such as *Kubernetes manifest*, *Flyway versioned migration*, *Helm chart values · production*, or *Test source root · module accent: payments*. Only context rules, project roles, environment variants, module accents, project icon overrides, and a few notable path mappings are described; plain extension matches add nothing, and existing IDE tooltips are kept with the description appended. Swing exposes a tree node's tooltip as its accessible description, so screen readers announce the same text. Turn it off with **Describe recognized files and folders in Project view tooltips**. Labels live in `IconDescriptions`, keyed by mapping key.

Run **Tools > Audit Project Icon Coverage** or right-click a directory in the Project view and choose **Audit Icon Coverage**. The cancellable audit uses the same resolver as the icon provider, groups generic and unmapped files by extension and parent folder, and lets you open a finding, create a project override, copy a suggested `icons.properties` mapping, or open a prefilled missing-icon report.

## Scopes

Emberkai also adds read-only scopes for **Find in Files**, the Project view scope selector, inspections, and **File Colors**: **Emberkai: Database migrations**, **Infrastructure** (including Ansible, Terraform, and SOPS-encrypted files), **Kubernetes & GitOps** (including Helm, Flux, and Argo CD), **API contracts**, **CI pipelines**, **Spring configuration**, **Production config** (files that would carry the production environment badge), **Generated files** (described below), and **Entry points** (Java and Kotlin files whose class is an application, web controller, message listener, or scheduled job, and Next.js routes and NestJS controllers, gateways, listeners, and scheduled jobs, as described above). Tool scopes use the icon resolver's context rules in the same priority order, so each file belongs to at most one of them. Scopes describe what a file is, so they ignore the icon category toggles. Only files are members; folders appear when they contain matching files. Spring XML DOM detection needs indexes and is not part of the Spring scope.

## Code owners

Repositories with a CODEOWNERS file get an ownership layer. Emberkai reads the first of `.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`, and `.gitlab/CODEOWNERS` in the repository root and follows GitHub's rules: the last matching line wins, unanchored names match at any depth, a trailing `/` covers a directory and its contents, `docs/*` covers only that level, and a pattern without owners marks a path as unowned. GitLab sections are read as GitLab reads them: a header such as `[Backend] @org/backend` gives its default owners to lines below it that name none, and each section contributes its own last matching line, so a path can collect owners from several sections; Explain This Icon lists every line that applied. Project view tooltips add *Owned by @org/payments* (turn it off with **Show CODEOWNERS owners in Project view tooltips**), **Explain This Icon** shows the owners with the CODEOWNERS line that assigned them, every owner gets an **Emberkai: Owned by …** scope for Find in Files, File Colors, and the Project view (up to 50 owners), and **Lens > Owned By** dims everything a team does not own. **Lens > Owned By > No Owner** and the **Emberkai: No code owners** scope show files that CODEOWNERS governs without giving them an owner, because no line matches or the matching line names none. The **CODEOWNERS pattern matches nothing** inspection (group **Emberkai**) flags lines whose pattern matches no file or folder, usually a moved or deleted path whose owners silently stopped being asked, and a CODEOWNERS file that is ignored because one in an earlier location takes precedence. **Tools > Find Reviewers for This Branch** compares the branch with the default branch the same way the **Changed on this branch** lens does (described below) and lists who must review it: each owner with the changed files they own, busiest first, then files with no owner and files no CODEOWNERS file governs. Deleted files count, matched against the folder they were in. Select an owner to see their files, double-click one to open it, or **Copy Owners** for a pull request; it needs the Git plugin. Excluded folders such as `build/` count as paths but are not searched. The search for CODEOWNERS stops at a nested Git repository, and parsed rules follow unsaved edits.

## Generated files

Generated files get a grey *generated* hint after their name in the Project view, with the reason in the tooltip. A file counts as generated when IntelliJ marks its source root as generated, or when its first 4 KB carry a phrase generators write: `DO NOT EDIT`, lowercase `@generated`, *auto-generated*, *automatically generated*, *This file is generated*, *Code generated by*, *Generated by the protocol buffer compiler*, or *Do not edit this file*. *Auto-generated* and *automatically generated* count only in the comments that open the file, before its first line of code, so Eclipse's `// TODO Auto-generated method stub` or a comment about an automatically generated primary key leaves a hand-written file alone. Prose files such as Markdown are skipped, and the `@Generated` annotation is ignored because hand-written code also uses it to opt out of coverage. Header-marked files are also reported to IntelliJ as generated sources, so the IDE warns when one is edited and names the header line that marked it. The **Emberkai: Generated files** scope covers both, which helps exclude generated code from Find in Files or inspections. Turn the hint and the IDE warning off with **Generated file markers**; the scope stays.

## Lenses

**View > Emberkai Icons > Lens** turns the Project view into an answer to one question. Files that belong to the lens keep their full icons and text, folders that contain them stay highlighted, and every other node is drawn dimmed, including native Java and Kotlin icons, with a tooltip naming the lens. Lenses: **Production blast radius** (production config, database migrations, and secrets that are not ignored by VCS, including plaintext Kubernetes Secrets), **Infrastructure** (infrastructure as code, Kubernetes, and GitOps), **API contracts**, **Entry points** (every way work gets into a service: applications, controllers, listeners, and scheduled jobs), **CI pipelines**, **Database migrations**, and **Spring configuration**. Membership uses the Emberkai scopes above.

The **Emberkai** status bar widget shows the active lens and the Spring profiles of the selected run configuration, such as *Lens: Database migrations · Profile: prod*. Click it to choose a lens, or one of the run configurations that activate Spring profiles; selecting one makes it the selected run configuration, which moves the live-profile marker. Hide the widget from the status bar's context menu. Turn it off under **Settings > Appearance & Behavior > Emberkai Icons > Lenses**.

**Depends on …** answers "what can a change to this module break?" Select a file or folder in a module and open **Lens**: the entry for that module highlights its files and the files of every module that depends on it, directly or through other modules, in any dependency scope. Dependencies come from IntelliJ's module graph, so a Gradle or Maven project shows the modules its build declares once imported. The lens follows changes to module dependencies.

**Changed on this branch** answers "what does this branch touch?" and is offered when the Git plugin is enabled. It highlights files that differ from where the branch left the default branch, including uncommitted edits and untracked files that are not ignored. In each Git repository the base is the first of `upstream/main`, `upstream/master`, the branch `origin/HEAD` points at, `origin/main`, `origin/master`, `main`, and `master`; without one, the lens shows uncommitted changes only. Git runs in the background only while this lens is active, and its result follows commits, checkouts, fetches, and edits. It is computed once in the background when a lens is chosen and again after file changes, and nothing is dimmed until it is ready. **Hotspots** answers "where is this codebase moving?", also with the Git plugin. It highlights the 30 files changed in the most commits over the last 90 days, keeping every file tied with the last place, and skips files changed only once; merge commits and deleted files do not count. Change the window, the number of files, and the minimum commits under **Settings > Appearance & Behavior > Emberkai Icons > Lenses**. Git runs only while the lens is active, and new commits update it.

**Failing tests** answers "what is still broken?" Run tests in the IDE, from one test to a whole suite, and it highlights the test files with a test that failed the last time it ran. A test that passes again, in the same run or a later one, leaves the lens, and so does one that is skipped or ignored; a stopped run changes nothing. Results come from the IDE's test runner, so the lens works with any framework the IDE runs tests with, such as JUnit, Kotest, Jest, and pytest. They last until the project closes, and the menu entry counts the files that hold a failing test, such as *Failing tests (3)*.

A lens is a view mode, not a setting: it is not saved, it affects only the Project view, and **No Lens** turns it off.

## Folder icons

The **JVM architecture folders** context category is opt-in. When enabled, Java and Kotlin source packages named `controller`, `service`, `repository`, `domain`, `dto`, `mapper`, `config`, `security`, `client`, `exception`, or `util` get distinct folder icons. `config` and `client` folders are shown only when a few immediate Java/Kotlin files indicate configuration or client code; checks are bounded and cached, including unsaved edits.

Folder icons use Emberkai's folder outline with IntelliJ-style role cues: blue corner squares for source-set/module containers, blue source folders, green test-source folders, yellow resource lines, and package cubes. With module-aware accents enabled, every IntelliJ module gets a stable palette color derived from its name: service roots use the full color, while source roots, packages, and their descendants carry a small module-color dot. Manual overrides and the reset action live in the Project and Tools menus. Java and Kotlin roots share the same source-folder style. IntelliJ's root model selects the role, including for custom directory names and Kotlin Multiplatform root types. Before import, `src/main/`, `src/test/`, and Multiplatform source sets such as `commonMain`, `commonTest`, `iosMain`, `jvmTest`, and `wasmJsMain` use the same cues for their `java/`, `kotlin/`, and `resources/` folders. Actual root markings take precedence over layout guesses. The `.idea/` folder gets an IntelliJ IDEA folder icon, while everything inside it keeps native icons. Library, excluded, generated, and unsupported language roots retain their specialized native icons. `.mvn/` uses the Maven folder icon, and other tool folders keep their own.

## Tool coverage

- Gradle icons cover Kotlin DSL scripts, `*.versions.toml` catalogs, and the `buildSrc/` and `build-logic/` folders. Plain `build.kts` remains an ordinary Kotlin script.
- Spring icons identify `application*` and `bootstrap*` YAML/properties files when an ancestor Maven/Gradle build file or `gradle/*.versions.toml` declares `org.springframework.boot`. Spring XML DOM descriptions also use Emberkai's Spring artwork. When the Spring Modulith plugin is installed, its package lock semantics are painted onto Emberkai folder icons, with a setting to turn the locks off. Small build files are checked using cached contents and modification stamps, including open editor changes; no dependency resolution or build commands are run. Active-profile markers read the selected run configuration's `--spring.profiles.active=` program argument, `-Dspring.profiles.active=` VM option, or `SPRING_PROFILES_ACTIVE` environment variable, in Spring's precedence order, and from `--args='...'` or the environment of Gradle `bootRun` configurations. The Ultimate Spring Boot configuration's **Active profiles** field is read when its internal accessor is available. The set is recomputed when the selection or configuration changes; other configuration types show no marker, and the marker needs the Java plugin.
